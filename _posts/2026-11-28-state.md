`:state()` lets CSS match a custom element according to state exposed by that element’s implementation. It gives component authors a styling hook for conditions such as “busy,” “expanded,” or “checked” without requiring a public HTML attribute or class.

The pseudo-class accepts one `<custom-ident>`. That identifier matches a value in the element’s `CustomStateSet`, available through `ElementInternals.states`.

```html
<x-loader>Loading data…</x-loader>

<script>
  class XLoader extends HTMLElement {
    #internals;

    constructor() {
      super();
      this.#internals = this.attachInternals();
    }

    set busy(value) {
      if (value) {
        this.#internals.states.add("busy");
      } else {
        this.#internals.states.delete("busy");
      }
    }
  }

  customElements.define("x-loader", XLoader);

  document.querySelector("x-loader").busy = true;
</script>

<style>
  x-loader:state(busy) {
    color: royalblue;
    cursor: progress;
  }
</style>
```

Here, setting the `busy` property adds the `busy` custom state. The selector `x-loader:state(busy)` then matches the element. Removing that state causes the selector to stop matching.

This is useful because it separates component state from document markup. Classes are easy for application code to overwrite accidentally, while reflected attributes become part of a component’s public HTML API. Custom states let the component own its internal state while still allowing consumers to style the host element with ordinary CSS.

That makes `:state()` particularly valuable for reusable web components and design systems. A component can expose stable, meaningful states without exposing its internal DOM structure or prescribing exact visual styles. Consumers remain free to choose how each state should look.

The feature is currently defined in the CSS Selectors specification as part of an Editor’s Draft. As with other draft features, details can still change, and support should not be assumed everywhere. Check current browser compatibility for both `:state()` and the associated `ElementInternals.states` API before relying on them. If unsupported browsers must receive equivalent styling, provide a fallback using an attribute or class.

Custom states are styling hooks only. A state named `disabled`, `checked`, or `expanded` does not automatically provide the corresponding browser behavior, form behavior, or accessibility semantics. Components must implement those separately where appropriate.
